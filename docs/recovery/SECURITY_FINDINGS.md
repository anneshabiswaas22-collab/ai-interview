# Security and history investigation

Baseline: `d2bed6f35367ac754b5364ef829db1de2def53bb`. This investigation uses Git metadata and static inspection in the isolated cloud workspace. It does not establish who controlled a GitHub account, and is not a production penetration test.

## Preservation and history evidence

- The checkout was clean on branch `work` before recovery. The recovery branch is `recovery/forensic-baseline-and-feedback`; the original ref remains intact.
- `/workspace/recovery-evidence/d2bed6f/repository.bundle` passed `git bundle verify`. The working-tree archive and per-file SHA-256 manifest are outside the checkout, with read-only file modes. These are local recovery safeguards, not an independently retained external backup or tamper-proof storage.
- `git rev-parse --is-shallow-repository` returned `false`; `git rev-list --all --count` returned 33 reachable commits before recovery changes. `git fsck --full --no-reflogs` reported no errors or dangling objects. The local reflogs record cloud checkout/branch creation; they do not recover older owner-machine activity.
- `git ls-remote --heads --tags origin` returned only `main` at the baseline SHA and no tags. No other currently advertised recovery branch was found. Deleted remote refs, GitHub audit logs, release/Actions artifacts and other forks were not available through this Git inspection.
- Commit `a610107` adds exactly four ZIP files, with zero text deletions or other modifications. Commit `259b85e` adds the 1,705 extracted files. Commit `f924eae` has 452 byte-identical (100%) renames, creates `PROJECT_STRUCTURE.md`, and deletes `docs/REPOSITORY_STRUCTURE.md`. The deleted document remains in Git and its ownership guidance has a successor in `PROJECT_STRUCTURE.md`. These facts support preservation/reorganization, not a finding of lost application code.
- History contains two self-reported author identities, with a change in the latest nine commits. All 33 commits report Git signature status `N` (no signature). Neither author metadata nor absence of signatures proves authorization or compromise. Owner confirmation and GitHub audit evidence would be needed to attribute changes.
- The inspected formatting commit `e7a9685` retains JWT algorithm/audience/issuer verification, token-version checks, password hashing and TOTP behavior. The recent `78a8d39` adds managed-proxy CA configuration without disabling TLS verification; `d2bed6f` prevents a host AWS profile from overriding synthetic mail-test credentials.

## Execution and credential review

Static inspection covered active manifests, all three root workflows, Dockerfiles, operational scripts, authentication/authorization boundaries, provider HTTP plumbing, upload parsing and selected reference-source execution paths. Automated scans accounted for all baseline tracked paths; they are not line-by-line review of every implementation.

- The three root workflows grant `contents: read`; no `pull_request_target`, automatic production deployment or direct interpolation of pull-request text into shell commands was found. Third-party Actions use version tags rather than immutable commit pins: a supply-chain hardening item, not evidence of malicious behavior.
- Only sample hooks exist under `.git/hooks`; no custom `core.hooksPath` was configured. No tracked symlinks or ELF/PE/Mach-O/Java native-executable magic candidates were found. Images, model assets, ZIPs and WebAssembly still require their own provenance review; this check does not certify binary safety.
- All tracked environment files are examples. A current-tree byte scan for private-key headers, GitHub token shapes, AWS access-key IDs and long `sk-` key shapes returned no candidate files. This is a limited pattern scan, not proof no secret ever existed in history, assets, logs, CI or a deployed system. No credential values were printed.
- Project-level package manifests contain no install/postinstall/prepare hooks. The active web predev/prebuild hook copies four MediaPipe runtime assets from the installed dependency to a local public directory. Dependency lifecycle behavior and registry ownership still depend on supply-chain integrity; frozen installation and package checksums should remain enabled.
- `infra/docker/api.Dockerfile` separately installs the locked pdfkit version with npm, but that step does not preserve the pnpm lock for pdfkit's transitive dependencies. Improve reproducibility in a separate build hardening change.
- `make down` explicitly deletes demo volumes; it is a destructive operational command and must not be used for recovery cleanup. AWS deploy/admin scripts perform real infrastructure/account operations and were inspected, not executed in this audit.
- The root `AGENTS.md` and the preserved DeepInterview agent instructions were read as data. They contain project/workflow guidance and a statement that the preserved LiveKit agent is a shell; no credential-exfiltration instruction or request to bypass user authority was identified in those files. This is not blanket trust of every document or model prompt.

No malware, credential exfiltration destination, authentication bypass or attacker identity was established by this bounded investigation. Absence of a detected indicator is not a clean bill of health for the entire historical/deployed system.

The focused privacy patch introduces no dependency, schema, network or provider-configuration changes. From `apps/interview-platform/apps/api`, `pnpm exec vitest run test/unit/http.test.ts test/unit/llm-adapters.test.ts test/unit/logger-redaction.test.ts` passed all 43 tests; these use synthetic responses and do not contact a real provider. `pnpm exec eslint src/integrations/http.ts test/unit/http.test.ts` and `pnpm exec tsc -p tsconfig.json` passed. Rolling back the two changed TypeScript files restores baseline behavior but also restores the disclosure risk; it does not require a data migration.
